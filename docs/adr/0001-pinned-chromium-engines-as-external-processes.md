# Pinned Chromium Engines run as external processes

Apps run on the Chromium milestone their Tizen TV actually ships (Tizen 3.0 = M47 up to 10.0 = M130), not one modern engine, because the point of the tool is to surface the bugs a real TV would show. That rules out Tauri's own webview: WebView2 can't go below M86 and only the latest two majors are available as fixed versions, Linux Tauri uses WebKitGTK, and Tauri 2 has no Chromium (CEF) runtime. So every Engine is a separate Chromium process, downloaded on demand from Chrome for Testing (M113+) or the Chromium snapshot archive (older), and driven over the Chrome DevTools Protocol.

## Considered Options

- **One modern engine, with Version Profiles changing only APIs, keys, user agent and resolution.** Lighter and faster, but it misses engine-level breakage (e.g. ES2017 syntax on M47), which was the main reason for building the tool.
- **Embed the Engine in Tauri's webview.** Impossible for old milestones, as above.

## Consequences

- Old Engines get no security fixes, and the M47 Windows build is 32-bit only. It runs on Windows 11 (#24 prototype, then #38).
- A portable Engine needs read access granted to the AppContainer SIDs after unpacking, or its sandboxed processes can't start (#24).
- Snapshot Engines are older than Chromium's headless mode, or have only the old one (before M109), whose window never minimizes, so a hidden App can't see itself hidden: a headless Session runs them in a window placed off the screen (`headless = false` in the Engine Manifest; #38, #51). Wayland compositors ignore window positions, so on Linux that window goes on a private Xvfb display instead, when Xvfb is installed (#42).
- The M47 Linux build's sandbox needs a setuid-root helper, which a per-user download can't install, so it runs without one (`sandbox = false`). So do M56 to M85, whose renderers don't start under the sandbox on current Linux (#51). It also links GTK 2 and GConf, which current distributions no longer ship. M56 links both too, and M63 GConf with GTK 3 (`docs/linux.md`, #42, #51).
- Engines are run as downloaded, verified against the pinned checksum, with one exception: the M56 Linux build exports its own HarfBuzz, which the system's Pango binds to and crashes on. Its exports are renamed after unpacking (`unexport` in the Engine Manifest, #51). Patching is kept to that: a symbol rename in the dynamic string table, which the Engine's own calls don't go through.
- Each Engine needs its own testing: a nightly job (#39) runs the in-page Shim suite on every Engine Manifest entry. On Linux it runs under a virtual display (Xvfb), which an off-screen window needs. While every Engine on a platform has a headless mode, the newest one also runs off-screen there so that path stays tested; on Linux the M47 Engine now covers it. Linux Engines that need GConf run on Ubuntu 22.04, the last release with it.
- Chromium snapshots are built without proprietary codecs, so the Engines up to Tizen 8.0 play no H.264 or AAC, which every TV plays in MP4 (measured, #105); Chrome for Testing has them. The `proprietary_codecs` build flag (`build/config/features.gni`: "Enables proprietary codecs and demuxers; e.g. H264, AAC, MP3, and MP4") is on only for Chrome-branded and Chrome for Testing builds, and no such build is archived per milestone below M113. Swapping in another FFmpeg library doesn't turn on the demuxers the flag compiles out, and building Chromium per milestone is out of reach. No Engine, Chrome for Testing included, plays MPEG-TS, MKV, MOV, AC-3, E-AC-3 or HLS, which TVs also play. Each such format raises the `media-format-unsupported` Diagnostic instead.
- CDP usage must stay within what M47 supports, or degrade where it can't. See ADR-0002. Measured on M47 (#38): no `Browser` domain (the window is measured from the page and minimized through the OS), no `Log` domain or `Runtime.consoleAPICalled` (console comes from `Console.messageAdded`), no page lifecycle states (a hidden App is paused in the debugger), screenshots of the window rather than the emulated screen (cut out and scaled), and only one debugging client per page (DevTools goes through a relay on the Session's connection).
- The GUI never hosts the App itself. See ADR-0006 for how the screen gets into the GUI.
